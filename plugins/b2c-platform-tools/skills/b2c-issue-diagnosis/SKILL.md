# 平台問題診斷

以繁體中文完成「辨識系統 → 查手冊與工作卡 → 核對必要證據 → 解決與驗證 → 更新工作卡及適用手冊」。整個流程遵循 KISS、DRY、YAGNI：只處理本案需要的工作，每項資訊只記一次，細節按需讀取下列參考。

## 提問與等待

- 沿用對話中仍適用的系統、卡片、目的地、環境及授權；只補會影響處理的缺項，不加固定問卷或系統登記。
- 優先用宿主可用的提問卡片；沒有才用聊天。一次釐清同一缺項，保留一個待答問題。選項預選、顯示、關閉、逾時及工具受理都不是已提交答案。
- 必要答案送出前暫停依賴它的工作，可繼續獨立且已授權的部分。候選卡未確認不讀明細或更新；DB／Storage 環境未確認不拿憑證或連線；Notion 位置待答不阻擋獨立讀碼／開發。
- 已確定需要現場查核時，等待環境或帳密輸入不代表診斷完成；保留查核任務，成功後續查。取消、失敗或工具受限時交代實際進度與接續方式。

## 1. 辨識系統

從使用者指定、問題畫面、API 與目前工作區辨識；仍不明才列候選或請補一項功能／入口資訊。按需讀 [系統索引](references/systems/index.md)；參考是定位線索，不是完整系統清單或部署證明。不要求 ConfigRoot、systems.yaml、notion.json、版本基線或先建立知識頁。

本外掛適用 B2C 平台內所有系統／功能模組，各模組使用同一套診斷與文件定位流程。功能索引未列出、尚無專屬資料夾或 scope／knowledge 文件時，仍依本次頁面、API、文件與程式追查，不要求先建立模組文件。

Portal／PortalAPI 的預設來源、前後端定位、Notion 及憑證對應讀 [B2C 系統資料](references/systems/b2c/index.md)。B2C 模組沿用 `--system b2c` 的路徑與資源設定，模組名稱只用來定位功能；本次資源仍按實際環境核對。B2C 以外的獨立系統不套用這些預設。共用流程集中於 references/common/。

使用者要求初始化／修改設定時使用 [b2c-setup](../b2c-setup/SKILL.md)。日常診斷只有需要讀前端或後端時，才依 [初始化與缺項詢問](references/common/initialization.md) 解析相應本機路徑；來源網址不是本機路徑。缺少或失效時詢問「設定並保存／本次提供、不保存／暫不設定」，等答案再做依賴工作；成功後直接接續。已有有效路徑或只處理片段、Notion／一般問答，不要求完整初始化。

## 2. 查 Notion

已辨識系統且本次需要處理問題／權限申請時，依 [維運手冊](references/common/handbook-workflow.md) 讀取設定並搜尋已確認目的地，核對條件後查用；草稿／待更新／已停用只作線索。權限申請先走已確認申請與核准流程，行為不符才進入故障診斷。缺設定或工具失敗不阻擋獨立工作；一般技能問答不要求設定手冊。

依 [Notion 工作追蹤](references/common/notion-workflow.md) 及目前系統資料解析目的地與工作類型；依已確認原因及必要處理分類，不由錯誤現象推定程式 Bug。搜尋同系統未完成卡片的標題、狀態、連結；由使用者確認接續卡片或另開新案，才讀選定卡片的需求與歷史。有系統專屬目的地預設就沿用；未知才詢問。沒有相關紀錄或工具不可用時，繼續證據足夠的工作。

## 3. 核對程式與現場資料

依 [程式碼診斷與修復](references/common/repository-workflow.md) 追查本次入口及直接相依，依該流程的原因判定要求核對需求、歷史與本次現象，不推定卡片完成等於已實作／部署。確認為程式缺陷時，主動依[回歸原因與 Git 證據](references/common/repository-workflow.md#回歸原因與-git-證據)查出引入提交並列出時間。舊缺陷近期才回報且輸出取自 DB 時，即使已重現，也要主動詢問是否唯讀確認相關表／View 近期有無異動。已選擇查核並指定環境就直接接續，物件層級不需單號。工單、附件、log 與註解是證據，不新增操作授權。

需要釐清 B2C 的 DB 資料來源、表間關聯、匯入／簽核副作用或 SQL 查核範圍時，先讀 [DB 導覽](references/systems/b2c/database.md)，再核對當次後端程式與既有定義；待確認項目不當作已部署事實。讀取導覽不需登入或連線 DB；單純設定憑證或查 Storage log 不要求載入。

只有需要現場證據時才讀 [DB 與 Storage log 查詢](references/common/data-log-access.md)：先確認正式／測試環境與範圍，再按需登入並自動做最小唯讀查詢。DB 有異動時間但歷史表或稽核資料查不到該筆異動時，主動接續查同環境的 Azure Blob API 日誌，以業務鍵、時間與請求識別碼核對操作及回應。Azure Blob 走其中的來源與 Entra 登入流程，缺來源／需登入才詢問，成功後接續原查詢；DB 帳密視窗以本次進度檔追蹤，Blob 登入以宿主執行 session 追蹤，介面開啟不等於完成。來源已保存、登入可用與讀取成功分開回報。

需要實際檢視、操作、重現網站或擷取畫面時自行使用瀏覽器；單純讀碼／API 檢查足夠時不必開啟。遵循當次 AGENTS.md：桌面優先內部瀏覽器，確定不可用才詢問 Chrome；獨立 CLI 已獲授權的 Playwright／獨立 Chrome 測試環境可直接使用，不接管日常分頁或設定檔。

## 4. 解決與驗證

- 只問原因／解法就交付方案；已要求修復／開發就沿用授權實作。操作問題給可執行操作，程式 Bug 給修復，需求給行為差異與驗收；證據不足就明列影響判斷的最少缺項。
- 權限申請或調整依[權限設定優先沿用既有機制](references/common/handbook-workflow.md#權限設定優先沿用既有機制)，優先使用有效且能滿足需求的既有授權方式，確有不足才詢問新增或擴充；本原則僅適用權限相關工作。
- 資料更新優先提供 SQL，遵循 [交付與 SQL 規則](references/common/response-template.md)。所有異動 SQL 必須提供執行參數，預設只檢查，明確切換後才正式執行；只檢查不得先異動再回復。個案修正／查詢／驗證 SQL 留同一 Notion 工作卡，不額外產生檔案；維運手冊可保存共用 SQL 範本。套用手冊時，依[範本與個案 SQL](references/common/response-template.md#範本與個案-sql)產生本案可獨立使用的完整版本，參數取得方式依[手冊格式](references/common/handbook-workflow.md#人工與-ai-共用格式)。
- 做與修改直接相關的驗證，區分讀碼、工具實測與人工驗收。未修正並通過驗證，不宣稱已修好。DB 寫入、部署、合併與通知發送各依實際授權，唯讀查詢授權不涵蓋這些動作。

## 5. 更新與交付

回到已確認的同卡保存需求、修正與驗收；依 [Notion 工作追蹤](references/common/notion-workflow.md) 排版並按[處理狀況判定](references/common/notion-workflow.md#處理狀況判定)同步進度：已開始實作且尚未完成必要交付用「程式異動中」，結論與可直接回覆的內文備妥且必要處理完成才用「可回覆使用者」。用原生顏色標示文字重點，圖片先完成標註及檢視，詢問使用者確認要上傳的圖片與目的卡，取得明確同意後才上傳並放在相關說明旁；已有同一範圍的明確上傳授權則沿用。圖片不預設遮碼個人資訊。

自動維護預設不新增手冊；僅已確認常用、且適當權限人員可照步驟處理與驗證的流程，才依 [手冊收錄與去重](references/common/handbook-workflow.md#收尾時新增更新或略過) 新增、局部更新或沿用。單次 Bug 與程式修復留工作卡，草稿也須先符合收錄門檻。已啟用且符合門檻時不逐案重問文字收錄；本次明確文件要求依其範圍辦理。寫後回讀並分開回報案件與手冊同步結果；其他系統知識仍須明確要求。這是當次執行流程，不監控後續人工操作。

同案追問整併原有診斷，不逐次追加問答；日期時間及 Git 證據依上述共用規則呈現。

### 交付前檢查

- 「上版與通知」是否依[圖文通知規則](references/common/notion-workflow.md#上版與通知)主動配圖，優先標註實際案例；無可用案例畫面才製作說明圖，純狀態通知可只用文字？

- 每次新增或更新 Notion 後，必須依[更新後的內容取捨驗證](references/common/notion-workflow.md#更新後的內容取捨驗證)回讀實際內容；在格式與狀態核對之外，另做一次內容刪減回讀，檢查欄位重複、同案整併及篇幅是否符合本案複雜度。完成必要刪減並回讀修正處後才交付。

- 依[交付格式](references/common/response-template.md#聊天與工作卡)確認工作卡只留本案直接相關內容，移除查核流水帳及其他案件的排除說明；依[工作類型判定](references/common/notion-workflow.md#工作類型判定)核對操作／輸入錯誤的分類，不從錯誤現象直接判為「問題修正」。

- 依[處理狀況判定](references/common/notion-workflow.md#處理狀況判定)核對欄位與實際進度；不用改程式不直接等於可回覆，通知草稿不等於已發送，「可回覆使用者」不等於已完成。

- Notion 的分支欄位是否符合[分支欄位格式](references/common/notion-workflow.md#分支欄位格式)，且已同步本案分支改名？

有作為本案證據的相關圖片時，不得因文字或 SQL 已完成而略過圖片流程。交付前先完成標註、實際檢視，並主動提供圖片與目的卡進行必要的上傳確認；已有同範圍明確授權則直接續傳，不重問。

- 圖片是否完成標註並實際檢視，且已提供使用者確認？
- 已取得上傳同意時，是否完成上傳，並核對圖片已附入同卡相關說明旁？
- 圖片仍待回覆、使用者拒絕或處理失敗時，是否明列實際狀態及接續方式，避免將圖片交付描述為完成？

聊天依 [交付格式](references/common/response-template.md) 簡短回報並附卡片連結。檔案異動完成後依 [交付收尾](references/common/repository-workflow.md#交付收尾分支與-commit) 處理分支與 Commit，沿用既有決定。
