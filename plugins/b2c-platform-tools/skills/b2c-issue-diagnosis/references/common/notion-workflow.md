# Notion 工作追蹤

## 目的地與工作卡

- 沿用使用者已指定的目的地與卡片，再讀目前系統資料中的 Notion 目的地預設，新案也保留適用的既有目的地；共用流程不硬編碼任何系統看板。需記錄而位置未確認且無適用預設時，提問提供「使用既有 Notion」「提供其他 Notion 連結」，列出可核對的既有位置，選其他後才請提供連結。
- 尚無選定卡片時，在同系統範圍以標題關鍵字及未完成狀態搜尋，只取標題、狀態、連結。缺狀態用屬性查詢補齊；無法取得就標未確認，不逐張讀全文，也不宣稱已排除完成項目。
- 找到候選即請使用者選接續哪張或另開新案；只有一張或同名也不能自行認定。已完成卡片只在使用者指定／要求追查時讀取；沒有候選才按本次需求建新卡。一般問答不必建卡。
- 確認後讀選定卡片的需求、歷史、驗收與必要附件，再局部更新同卡。保留人工勾選與歷史；歸屬／需求有矛盾時補問差異，不改標題掩蓋問題。卡片被刪除或失去存取時先回報，不擅自重建或換目的地。
- 同案追問更新原有診斷、修正或驗收明細，合併重複結論並修正已被新證據取代的說明；不要按每次提問追加獨立章節、時間線或問答紀錄。保留必要證據、commit 連結、SQL、圖片及人工勾選；不同問題確需另列時才增加項目。
- 新卡沿用現有 schema、欄位及選項，不增欄位。標題用「系統｜主詞＋動詞＋變更或異常」，例如「Forecast｜CPU 數量卡控改採機種前 7 碼」。依實際進度填狀態與工作類型；負責人、日期未知就不填，分支依下方[分支欄位格式](#分支欄位格式)記錄。

記錄授權沿用本案已確認決定，使用者要求不寫入時遵從。遠端權限、目的卡確認與其他操作授權各自成立；失敗不清除原決定。必要需求、個案對象／核准、SQL 與驗收留同卡；本次實際採用的維運手冊只附連結。依 [手冊流程](handbook-workflow.md) 在已確認目的地與啟用範圍內，只收錄符合常用及可照做門檻的共用步驟，不整卡複製，也不擴建其他系統知識頁。內容取捨及 SQL 交付依 [交付規則](response-template.md)。

## 分支欄位格式

- Notion 的「分支」欄位統一填 `專案名稱：完整分支名稱`，例如 `GlobalBizAPI：joyce/fix-sql-injection`。專案名稱使用已核對的 Git 儲存庫名稱，以區別前後端；保留完整分支名稱及其前綴，不以卡片標題的系統／模組名稱代替儲存庫名稱。
- 同卡涉及多個儲存庫時，每個已確認的專案／分支各列一筆，以換行分隔；即使分支同名，也各自保留專案名稱。只記錄本案實際使用的分支。
- Git 分支改名後，同步更新此欄位及本文中本案的目前分支名稱，保留專案前綴。既有欄位只有分支名稱時，核對來源後補上專案名稱；專案或分支尚未確認就不猜填。此為 Notion 顯示格式，不改寫實際 Git 分支名稱。

## 工作類型判定

依已確認的原因與必要處理方式分類，不以「異常、錯誤、修正」等需求用詞、錯誤畫面、驗證失敗或報表結果直接分類為「問題修正」。沿用看板現有選項及使用者已定義的分類；下列為對應選項存在時的判準，不新增欄位或選項：

- **維護**：使用者操作或資料輸入錯誤、資料誤植、設定／權限調整或例行資料處理；現有程式依既定規則運作，僅需更正操作、輸入或資料，無須修正邏輯。例如匯入數量誤填文字、操作選錯範圍或機種平台資料誤植。
- **問題修正**：已確認程式或資料庫程序違反既定需求，必須修正邏輯；須記錄預期規則、錯誤分支或行為，以及核對證據。只修改資料、使用者操作／輸入有誤或畫面出現錯誤，不構成程式缺陷證據；不得因順帶發現與本案無直接關聯的缺陷而將本案改歸「問題修正」。
- **功能調整**：新增能力或改變既有業務規則；須記錄變更前後的預期行為差異。
- 原因或必要處理尚未確認時，工作類型先留空，處理狀況依實際進度填「處理中」；不為填滿欄位猜測原因。現有 schema 不允許留空或無對應選項時，只補問分類方式。
- 診斷完成後重新核對工作類型；混合工作依主要必要處理判斷，並記錄其他影響。不覆寫使用者已確認的人工分類；新證據與該分類衝突時先說明差異再確認。工作類型與診斷 JSON 的技術分類分開判定，不機械互相映射。

## 處理狀況判定

依本案實際進度選擇，與工作類型分開判定；以下選項存在時才使用，不因診斷自動新增欄位或選項：

| 處理狀況 | 使用時機 |
| --- | --- |
| 待辦 | 已登記，尚未開始處理。 |
| 處理中 | 正在分析、補證據、準備方案，或處理資料、設定及權限；已確認需改程式但尚未開始實作時也用此狀態。 |
| 程式異動中 | 已確認需修改程式或資料庫邏輯，且已開始實作；尚待完成必要驗證、人工驗收或部署時維持此狀態，在處理清單記錄具體進度，不宣稱已上線。 |
| 可回覆使用者 | 原因及處理方式已確認，必要修正、驗證與部署已完成或本案不需要，且「上版與通知」已備妥可直接回覆的內文；僅需使用者依指引操作的案件也可使用。 |
| 已完成 | 本案必要工作、人工驗收與通知均完成；沿用已確認的人工勾選，不要求使用者重複回覆。有完成時間欄位時填實際完成時間，不以最後編輯時間代替。 |

- 「程式異動中」與「可回覆使用者」都屬進行中，不是完成狀態。操作／輸入問題通常為「維護＋可回覆使用者」；不用改程式但仍待修資料、調整設定／權限或核對結果時，維持「處理中」。
- 「可回覆使用者」不代表已寄送、已修正使用者輸入或已取得操作結果；回覆內文須分清已完成處理與請使用者執行的步驟。通知草稿不等於已發送，狀態切換不授予寄送、DB 寫入或部署權限。
- 有尚待實作的本案程式缺陷時，不因已有暫行操作方式而改為「可回覆使用者」。後續發現仍需修正或補證據時，依實際進度回到「程式異動中」或「處理中」，更新同卡結論。
- 搜尋未完成卡片時包含這兩個進行中狀態。更新前核對實際 schema；缺少對應選項時沿用可用的「處理中」並回報差異，不自行修改看板 schema，也不將診斷 JSON 的 ANSWERED／FIXED 直接當作已通知或結案。

## 結構與進度

外層依序保留：

1. 「處理清單」一般標題及 checkbox。
2. 「處理明細」一般標題及標題式收合明細；用 `01｜名稱`、`02｜名稱` 連續編號，清單與明細一一對應。項目依本案增減，必須有獨立的「實際驗收」及其後的「上版與通知」，不固定五項，也不加空的資料庫／部署工作。
3. 「處理歷程」獨立收合標題；以使用者時區的實際記錄時間 `yyyy/MM/dd HH:mm：內容`，新到舊，每筆一兩句，不用日期 mention。只記重要處理進展，不逐次抄寫問答；保留影響判斷的既有歷史。

待辦與完成狀態只列在頂端 checkbox；明細保留實際修改、操作、預期與已取得結果，不重述待執行狀態。人工驗收勾選／狀態可作使用者確認，下次讀取時沿用，不當成工具實測；不要求另回覆一次，也不承諾背景監控。只有 Skill 工作與人工項目均完成才結案。

本文、Git 證據與處理歷程的日期時間統一使用 `yyyy/MM/dd HH:mm`，先換算至使用者時區；Notion 日期 mention 無法保持此顯示格式時改用純文字。事件時間依事件證據，記錄時間依實際記錄時刻，不以頁面最後編輯時間代替。來源只有日期時保留已知日期並註明「時間未確認」，不補造 `00:00`；既有時間無法核對時不猜改。

### 採用維運手冊的工作卡

提供手冊來源連結、必要參數摘要，以及依[SQL 交付規則](response-template.md#範本與個案-sql)備妥的完整操作／驗證內容。驗收保留預期與實際結果的對照；尚無實際結果時留空，不預填成功。來源連結旁不附加「草稿」字樣；手冊本身的狀態與適用性仍依[手冊流程](handbook-workflow.md)判定，不藉移除字樣將未驗證內容視為可使用。

進度沿用上節的頂端 checkbox 規則；回讀時刪除標題、摘要、明細或歷程中僅重述「尚未執行／待驗收」的文字。保留影響操作的範圍差異、必要確認條件及實際證據，不以精簡為由移除。局部修訂保留人工勾選及既有有效內容。

## 文字重點用色

主動用 Notion **原生文字顏色**標出重要差異及條件，不能只靠粗體或 SQL 語法高亮：修改前／錯誤值用紅色，修改後／目標值用綠色，執行範圍與必要條件用橘色。只著色關鍵詞與數值，不整段染色；同義用色保持一致，避免把目標值綠色誤寫成已驗證完成。

Notion Markdown 用 `<span color="red">文字</span>` 等支援色彩，原生 API 用對應 rich text 的 `annotations.color`。不要使用 CSS、`<mark>` 或把標籤放進 SQL／行內程式碼裡。

```markdown
- 將平台由 <span color="red">原錯誤值</span> 改為 <span color="green">目標值</span>。
- 僅處理 <span color="orange">本次已確認的週別與料號</span>。
```

這些是格式示例，不是可套用的業務值。寫入後核對顏色是否保存；工具只回純文字時，進一步讀取區塊格式或實際頁面確認，不能用「寫入成功」推定重點已上色。

## 圖片標註與上傳

- **主動完成圖片準備，再確認上傳**：收到或取得本案相關證據圖片後，先完成標註並實際檢視，主動提供可檢視的圖片及已確認的目的卡，詢問並取得明確上傳同意；不能等使用者追問才補做，也不能以尚未取得同意為由略過標註、檢視及提問。等待答案時可繼續獨立且已授權的文字整理。建立／選定卡片、同意記錄文字、提供截圖或工具核准，都不等於同意上傳圖片，不先傳檔再補問。
- 同一批明確列出的圖片及同一目的卡已有使用者明確上傳授權時沿用，不重問；新增圖片或更換目的地需另行確認。使用者拒絕／取消或仍未回答時不傳檔，也不附入卡片；宿主工具審核照常，不擴及其他目的地或無關附件。
- **不預設遮碼圖片中的姓名、帳號、聯絡資訊等個人資訊**；只有使用者要求時才遮碼。登入憑證與秘密的處理依 [存取規則](data-log-access.md#秘密與連線取用)，不把個人資訊遮碼當成一般上傳前提。
- 有原始案例畫面時，在單張原圖副本上直接標註，保留原圖；不拆成「重點圖＋原始圖」或重複貼圖。每個需補標的重點使用簡短說明及指向對象的箭頭，框線／數字按需增加；已有足夠標記時沿用。
- 同項目的文字、箭頭、框線及編號同一主色，圓點內字可用黑／白保持對比。文字靠近對象、箭頭不交叉；可覆蓋不重要內容，但關鍵欄位、數值、錯誤及上下文必須可讀。數字只用於順序／流程，不為裝飾增加元素。
- 不改寫原文或用生成圖片取代證據。上傳前檢視實際副本的指向、顏色與可讀性，實際上傳該副本；圖片緊接相關來源、需求或驗收文字，以獨立圖片區塊呈現，不另開圖片章節／清單項目。
- 來源只交代一次；圖片已清楚就不加圖說，不加提供日期、重複主旨或製圖規則說明。取得／標註／上傳失敗在聊天回報具體缺項，不在卡片用工具過程代替圖片。既有同卡缺標註且可取得原圖時，局部補上，不重建整張卡。

## 實際驗收

依序放前提短段落、必要 API 表格、連續編號步驟。前提寫出設定入口／欄位及有效值；情境用 `1.`、`2.`…各寫「情境：操作 → 預期結果」，不另加重複案例或驗證相同數值。

API 表格固定為「異動」「Method／API 路徑」「本次變更」，只列本次新增／修改或驗收必須直接呼叫的 API；沿用時說明驗收用途。SQL 修正並以畫面／匯出檔驗收，不必列純追查讀過或未採用的 API。一般參數參考 Swagger，修正必需的具體傳值與防止整筆覆寫的做法仍須交代，見 [交付規則](response-template.md#涉及程式資料庫變更的交付)。

## 上版與通知

只放可直接寄給需求提出者的通知內文，以業務用語說明功能影響、操作變化與必要配合；沒有配合事項就省略。預告、邀請驗收或更新完成依實際進度措辭，不虛構上線；不需部署仍提供結果通知。

不加通知主旨／擬稿標籤、程式路徑、測試項數或「修正交付後／待授權／依 SQL 執行」等內部措辭，也不要求業務使用者安排部署。草稿完成不代表已發送。

原則上圖文並茂：涉及操作方式、畫面欄位、資料結果或流程變化時，主動配圖，讓使用者看懂變更重點、預期結果及必要配合，不等使用者追問。純進度或完成狀態通知，文字足以說清楚時可不附圖；不為湊圖重複貼圖或製作裝飾圖。

- **優先標註實際案例**：先從本案截圖、附件（含 Excel）或系統畫面取得相關實際畫面，在副本加上指向對象的箭頭及簡短文字；不能只原封不動貼上原圖。已有足夠標註時直接沿用，不必每次重新製圖；有案例附件但尚無截圖，不直接視為沒有案例。
- **沒有可用案例畫面才製作說明圖**：依已確認的功能與規則製作流程、操作或結果比較示意，清楚標示「示意」，不重繪成貌似實際驗收的截圖，也不以生成圖片取代已有的案例證據。
- **對準實際影響**：箭頭與文字指向本次真正受影響的欄位、明細或步驟，不圈選未參與處理的彙總列或無關內容；保留必要上下文及可讀性。前後結果只用已核對證據，尚未實測的修正後結果標為「預期結果」。圖片緊接對應說明，製作、檢視及上傳沿用[圖片流程](#圖片標註與上傳)。

## 寫入與核對

使用 Notion MCP 前，先讀取該連線的 `notion://docs/notion-flavored-markdown-spec`；同一規格已讀且適用時沿用。標題式收合的名稱必須是開啟標籤後的本文，與子內容間留一空行；原生 API 則用 `heading_2.rich_text`、`is_toggleable: true` 及 `children`，不以屬性或子段落代替標題。

粗體須實際套用格式；中文標籤與內文相鄰，或 Markdown 被存成字面符號時，依連線規格改用 `<b>標籤</b>` 等原生格式並核對，不把可見的 `**` 當作已加粗。

以下只示範結構，明細名稱、數量及內容按本案調整：

```markdown
## 處理清單

- [ ] 01｜問題與修正
- [ ] 02｜實際驗收
- [ ] 03｜上版與通知

## 處理明細

<toggle heading="h2">
01｜問題與修正

問題、修改項目與本案核對的 SQL；圖片放在相關說明旁。
</toggle>

<toggle heading="h2">
02｜實際驗收

必要前提及 API 表格（需要時）。

1. 情境：操作 → 預期結果。
</toggle>

<toggle heading="h2">
03｜上版與通知

面向需求提出者、與實際進度一致的通知內文。
</toggle>

<toggle heading="h2">
處理歷程

以實際 yyyy/MM/dd HH:mm 時間記錄重要變化。
</toggle>
```

寫入前後核對診斷是否已整併、日期時間格式、commit 連結、粗體與原生顏色、圖片位置，以及標題文字、編號／清單對應與必要驗收及通知。使用已儲存回傳內容確認；缺格式資訊、有警告或疑似空白／「Heading 2」標題時，再讀對應區塊或檢視頁面。局部修正並保留圖片、SQL、歷史及人工勾選，不重建整卡；仍無法確認就回報未完成的具體項目。

### 更新後的內容取捨驗證

每次新增或更新 Notion 後，必須重新讀取實際儲存的內容，逐段及逐條套用[交付規則](response-template.md#聊天與工作卡)：「刪除後是否影響本案判斷、修改、執行或驗收」；不影響就刪除。只保留與問題及修改直接相關的必要結論、操作與驗收，省略例行檢查結果、未變更事項、測試過程及重複說明；直接影響本案結論者保留必要資訊。

發現可刪項就局部修正，再回讀修正處確認；保留必要的證據、操作條件、人工勾選及影響判斷的歷史。檢查及刪減過程不另寫進工作卡或處理歷程。無法回讀時，回報內容驗證尚未完成，不以工具寫入成功代替。
