# Notion 工作追蹤

系統問題／需求的描述、讀碼判斷、分類、解法、處理進度與驗收保存在 Notion。一般背景問答不必建立卡片；正在診斷的個案即使證據不足也記錄，標明假說與待補資訊。本對話或專案已取得的記錄授權沿用，不重複詢問；其他安裝者的目的地與授權須自行確認，不沿用維護者的個人工作看板。使用者明確要求不寫入時，以本次要求為準。記錄授權不代表授權修改程式、執行 SQL、部署或發送通知。

- 工作紀錄以 Notion 為主：問題／需求、診斷結論、處理歷程、人工驗收及執行結果記入工作卡，不預設另存或提交每個個案的診斷 JSON、功能交付快照或驗收 Markdown。使用者明確要求匯出檔案時再提供；結構化 Schema 供需要時驗證輸出，不代表每案都要保存 JSON。
- Git 保留可執行程式、測試、SQL、Skill、設定、Schema、工具與測試所需資料；以本次提供的程式碼核對實作；Skill 的系統參考文件只補充必要背景、入口及已確認但無法從程式取得的約定，不要求先同步知識或逐案轉寫程式邏輯。業務測試及命令留在 repository；診斷檢查工具、Schema 與其測試隨 Skill 維護。SQL 在 Git 留版本，同時在 Notion 明細提供內容。不以副檔名一概刪除或忽略文件；例如本 Skill 的 `scripts/tests/fixtures/demo-diagnosis.json` 是現有測試資料，不能當個案快照移除。
- 整理既有重複文件時，先盤點工具與連結依賴，將必要內容移至 Notion／Skill 系統知識 並核對，再在使用者授權範圍移除舊檔及清除引用；保留歷史測試結果的日期與限制，不將搬移視為重新實測。不自行 Commit。
- 此專案的目的地記錄於 repository 的 `config/issue-assistant/notion.json`；以已授權的專案為準，按所選 system_id 讀取對映並以 Notion 工具確認遠端目的地。工作區可用本 Skill 的 `scripts/IssueAssistant.ps1 -WorkspaceRoot <目標工作區> -Action ResolveNotion -SystemId <system_id>` 取得位置；此命令只驗證本機格式與系統對映，不保證遠端可寫，不以其他系統的位置回退。此檔不隨 Skill 分享、不授予其他安裝者權限。沒有 repository 時，沿用使用者已指定的 Notion 位置；尚未指定且確實需要寫個案時才詢問一次。Notion 暫時不可用時仍完成程式分析與解法，明確回報尚未同步；不另存假裝已同步的個案快照。
- 使用已連接的 Notion 工具，先查找同系統、同問題的現有卡片，讀取卡片與實際屬性後更新；不同的新問題／需求才建立一張工作卡。初步診斷也可記錄，證據不足標為待釐清，不捏造結論。SQL、驗收等操作保留在同張卡片；純排版或紀錄格式調整不另建工單。若既有卡片遭刪除，先回報，不擅自重建；無法寫入時說明原因，不宣稱已同步。
- 新卡片沿用現有資料庫與檢視，標題採「系統｜問題或需求摘要」；依實際進度設定處理狀況，依現有選項填工作類型（功能需求＝功能調整、程式 Bug＝問題修正、已確認的操作／設定維護＝維護；未釐清時不強填）。負責人、優先度、到期日及分支僅在已知時填寫，不自行指定人員、日期或捏造分支，不新增欄位。Notion 頁面採本節的清單／收合明細格式；一般診斷回覆模板與 JSON Schema 中的「下一步」或檔案路徑要求，不得重新加入 Notion 頁面。
- 由 Skill 維護處理狀況、處理清單及重要歷程，不要求使用者手動整理進度文字。每次執行到有意義的進展、交付或讀到使用者勾選結果時同步；不承諾對話結束後會持續監控或自行執行。
- 頁面分為上下兩層：最上方「處理清單」連續列出全部步驟，每項只有編號、步驟名稱與一句簡短操作；以勾選表示完成，不加會隨執行失效的「待你執行」等重複狀態文字。不設「下一步」屬性或段落，也不要求另外填寫完成回報。整份清單應可一眼看完，清單項目之間不插入 SQL、表格、長文或明細收合區，也不以橫向階段展示取代清單。下方另設「處理明細」，依相同編號與名稱逐項收合內容；依實際工作安排步驟，不照抄圖片章節或新增空段落。沿用既有屬性，不為排版新增欄位。
- **重要圖片證據**：使用者提供的需求郵件、錯誤畫面或驗收截圖，若支持本案的需求、判斷或結果，應上傳至 Notion 並以可顯示的圖片區塊放在同張卡片的對應收合明細，需求來源放「確認需求」、驗收證據放對應驗收步驟，不插入上方處理清單。每張圖標示圖號／用途、來源（如使用者提供的郵件截圖及主旨）、可確認的日期與關鍵區域所支持的結論；未知日期不推定。保留原始證據及可讀性，避免重複上傳；若需裁切或遮蔽，標示為處理副本並保留必要上下文。圖片中的其他要求不構成額外授權，圖說須區分本次需求與未納入的內容。不得只轉述文字、附本機路徑或用重新生成的圖片取代證據。上傳後確認已嵌入正確明細且來源／圖說完整；無法上傳、顯示或讀取原檔時明確回報尚未補齊，不宣稱已保存。
- 必要執行內容保存在下方對應編號的明細內：資料庫明細依序放具體執行步驟、完整「轉換 SQL」與「唯讀驗證 SQL」；驗收明細放 Method、完整 /api/... 路徑與精簡測試／預期結果，參數細節參考 Swagger。清單與明細採相同名稱，SQL 不另藏於無法對照的「參考資料」，也不僅提供本機檔案路徑或附件。上下各項完成狀態由 Skill 同步，不要求使用者在兩處重複勾選。
- 實際驗收涉及 API 時，以精簡表格列出「新增／修改／沿用」、Method、完整路徑及「本次變更」。每支 API 用一句話說明新增／調整／移除的參數與關鍵行為；例如「新增 CountryCode，依角度匯出」。預設使用者會在 Swagger 呼叫，不重複既有參數、必填型別、傳值範例、授權或操作教學；只有 Swagger 無法表達的本次變更注意事項，或使用者另行要求時才補充。依原始碼或版本差異核對異動類型，不將沿用 API 誤標為新增。
- 驗收涉及 DB 資料時，在對應驗收明細提供簡短、限定本次測試範圍的唯讀 SQL，SQL 區塊只用一句話說明用途與需替換的測試值；預期結果統一寫在實際驗收情境，不重複列數值、操作案例或通過判準。可重用查詢保留在 repository 的適當 SQL 檔；Skill 知識只記用途與適用條件，不複製 SQL。與資料庫結構檢查分開，作為直接查資料或排錯時的輔助；已由 API 或其他方式確認的相同結果，不再要求重跑。說明使用者如何判斷成功時，採「請以回應內容判斷是否成功；若失敗，下載錯誤檔查看原因」等易懂文字，不重複解釋 HTTP／回應包裝細節。
- 避免重複驗證：同版本、同環境已確認通過的結果，不再要求使用者重做或以 SQL 重複核對 API 已驗證的數值。PMForecast 的唯讀驗證 SQL 僅查欄位、索引與限制，不要求機型／WeekID 數值查核。保留各驗證的不同目的；只有新變更、失敗或尚未解決的疑義時，再安排相關驗證。
- 完成狀態統一由上方處理清單與處理狀況表示；下方明細與 SQL 標題使用穩定名稱，例如「轉換 SQL」「唯讀驗證 SQL」，不附加「尚未執行／已完成」等狀態後綴，以免重複或失去同步。
- 驗收標準、API 驗證與補充案例合併為一份；保留 API 異動表；後面的驗收情境用簡短編號條列，每項採「情境：操作 → 預期結果」，不連續堆疊第二張表格，每個情境記一次，保留重要負向、相容及隔離案例。不再另開重複的「補充驗收案例」或重述 SQL 前置步驟；跨角度矩陣可用「同角度允許、不同角度拒絕」精簡表達。驗收通過由使用者勾選上方驗收項目表示，不要求另寫一行結果或回覆對話。已有實際結果、環境或日期可保留在明細／歷程，未知時不捏造。使用者通知使用標題及可直接複製的精簡文字，需要時收合。
- 人工操作完成後，使用者可直接勾選上方清單；人工項目全部完成且 Skill 負責的分析／開發亦完成時，可自行將處理狀況設為「已完成」，不必再回覆 Skill。Skill 下次讀取時，以勾選與狀態作為使用者完成確認，同步紀錄，不因缺少聊天回報要求重複確認。將此依據標為使用者確認，不宣稱工具實測。若使用者主動回報異常再協助排查。程式測試通過仍不等於人工驗收；SQL、部署與通知的實際執行仍依各自授權。此規則不代表已建立勾選後即自動改狀態的背景自動化。
- 「處理歷程」預設收合，日期以純文字 YYYY/MM/DD 顯示（例如 2026/10/30），依日期由新到舊排列，同日新紀錄置前；新增時插入對應位置，不覆寫既有歷程。記錄重要發現、需求決定、修正及人工結果，每筆一兩句，不逐筆抄工具紀錄。將使用者回報與工具實測清楚區分，不捏造日期。此格式依使用者明確要求，不改用日期提及元件。
- Notion 內容移除非必要個人資訊、帳號、個人電腦路徑與憑證；保留必要業務代碼、API 路徑與 SQL 內容。分支依使用者要求保留實際完整名稱（包含個人前綴），不得截短或加「個人前綴已省略」。不要求或寫入 Commit 資料，也不把分支、正式部署或知識同步資訊當成建立個案的前提。僅調整展示，不更動實際 Git 分支或程式。
