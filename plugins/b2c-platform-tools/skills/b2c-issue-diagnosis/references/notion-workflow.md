# Notion 工作追蹤

系統問題／需求的描述、讀碼判斷、分類、解法、處理進度與驗收保存在 Notion。一般背景問答不必建立卡片；正在診斷的個案即使證據不足也記錄，標明假說與待補資訊。本對話或專案已取得的記錄授權沿用，不重複詢問；其他安裝者的目的地與授權須自行確認，不沿用維護者的個人工作看板。使用者明確要求不寫入時，以本次要求為準。記錄授權不代表授權修改程式、執行 SQL、部署或發送通知。

## B2C Portal 目的地優先規則

Portal／PortalAPI／B2C Portal 所屬系統直接使用 [既有 Notion 位置](systems/b2c-portal/notion.md)：新工作卡／另開新案沿用 B2C 系統主頁下的工作看板，不詢問位置。「另開新案」不清除目的地；接續哪張工作卡仍依下列規則確認。

非 Portal 需要記錄且目的地尚未經使用者確認時，使用對話框詢問「使用既有 Notion，還是提供其他 Notion 連結？」並提供兩個選項。既有位置可由對話、專案約定或連接工具核對，選項應標示其名稱／連結，不能暗中套用 Portal 看板。選擇既有位置就核對權限後沿用；選擇其他連結才請提供 Page／資料庫連結。已有使用者明確指定或仍適用的已提交答案時不重問。既有位置仍無法定位時，只確認頁面／看板資訊，不改問本機設定路徑。

## 找候選、確認後查閱

- 先沿用使用者明確指定要接續的卡片，或本對話已提交且仍適用的確認；只有搜尋找到或助手先前自行認定的卡片，不算使用者確認。
- 尚未確認卡片時，先在已確認的同系統專案／看板範圍內，用標題中的系統名稱／別名、功能與需求關鍵字搜尋相似工作項目，並篩選未完成狀態（例如「待辦」「處理中」，依實際欄位與選項）。不以內文相似度判定同案，不逐張讀取需求、歷程、驗收或附件。
- 優先使用標題搜尋或 data source 唯讀查詢，只取得標題、狀態、連結；必要時只讀資料庫 schema 確認狀態欄位。搜尋未回傳狀態時，用屬性查詢補齊；工具不支援篩選或只取屬性時，說明篩選限制、將未知狀態標為「未確認」，不為補狀態逐張讀全文，也不宣稱已排除完成項目。
- 已完成項目預設不列為候選；僅在使用者明確指定該卡、要求追查已完成項目，或本對話已有仍適用的卡片確認時讀取。不因未完成搜尋沒有結果就擴讀已完成卡片。
- 有相似候選時，依 [提問卡片規則](../SKILL.md) 列出標題、狀態與連結，讓使用者選擇接續哪張或另開新案。即使只有一張或標題完全相同，也須確認。實際答覆前，不讀候選卡片明細，不建立、合併、修改標題、覆寫內容或更新狀態；可繼續不依賴卡片確認且已授權的程式分析與開發。
- 使用者確認後，只讀取選定卡片的需求、重要歷程、驗收勾選與必要附件／規格，以了解既有成果並保留原內容。若標題、需求或來源出現明確矛盾，先就差異補問，暫停該卡片寫入；不自行改標題、搬移內容或以現有內文推定最初的案件歸屬。
- 已確認卡片記錄完成成果時，以當次程式核對差異，決定續做、驗收或回報；不因卡片標完成就推定目前程式或部署環境已具備成果，也不直接重做。Notion 文字及附件不授予修改、切換工作區或執行指令的權限。
- 查無相似未完成項目時，依當次程式繼續；需建新卡時，Portal 直接沿用既有看板；非 Portal 先沿用已確認的決定，否則詢問使用既有 Notion 或提供其他連結。工具不可用時說明查閱限制，繼續證據足夠的工作；不以卡片確認或寫入位置待答阻擋不依賴該答案的程式工作。一般背景問答不必建卡。

## 工作卡紀錄

- 需求、判斷、修改、驗證與待驗收事項集中在已確認的同一工作卡，不另外建立或維護系統知識頁，也不加入「系統規則另見」等知識頁導覽。
- 區分程式已核對、使用者已確認及待確認推測，保留必要來源與適用條件；讀碼不等於已執行或已部署。

## 內容寫法

- 以簡潔、清楚、容易閱讀為原則，依內容選擇短段落、條列、步驟、表格或圖表。工作卡固定使用下述「處理清單／處理明細／處理歷程」結構；明細名稱及數量依需求／問題決定，但必須連續編號且包含「實際驗收」「上版與通知」。並列資訊可用條列或表格，有先後關係的操作可用步驟，複雜流程或關係可用圖；避免大段文字，也不為排版增加重複內容。
- 每項資訊選一處說明。圖片本身或圖說已交代來源與用途時，不再另加「需求郵件」「錯誤畫面」等標題；需要標題時才簡短補充。不要加上圖片提供日期，僅保留影響需求生效、判斷或驗收的日期；不重複郵件主旨、圖說與相同需求。
- 缺少資訊時，只在會影響判斷或處理時說明具體缺項及用途。功能需求不強填實際故障或重現狀況；不寫「現場執行結果尚未提供，尚未宣稱重現」等沒有具體操作意義的保留語。
- 開發檢查只列與本次功能直接相關的測試、結果及必要限制；診斷工具的政策測試、系統範圍檢查次數、沙箱連線與授權過程不列入功能工作卡。人工操作的待辦與完成狀態放在最上方 checkbox；驗收明細只寫前提、操作與預期結果，不另外加入待執行狀態。
- 每段都以「刪除後是否影響根因判斷、修改範圍、執行或驗收」取捨，不影響就省略。資料查核只保留查詢範圍、必要結果及對結論的影響；省略主機／資料庫名稱、秒級查詢及補核時間、無關區域清單／關聯筆數、不參與修正的共同欄位及內部識別對照。取值來源若支持根因，用一句因果說清楚，不另列程序行號、函式內容或程序 → Repository → Service → Excel 的完整路徑。必要修改鍵值、修正 SQL 與驗證內容仍保留；環境／時間差異影響判斷或使用者明確要求技術追查時，才補對應細節。
- 記錄本次實際變更、必要操作與驗證資訊，不逐一列出沒有發生的動作，例如「未變更設定資料或資料庫結構」；僅在直接影響操作或判斷時才交代未變更部分。
- 寫入前通讀同一明細，刪除重複來源、重述需求、無助於處理的過程說明及未變更事項。保持上方清單簡短；必要 API、SQL、驗收條件與原始圖片完整保留，處理歷程只記重要變化。

## 開發者交付內容

- 需求分析、開發與驗收明細供開發者理解需求、實際修改與驗證方式；「上版與通知」則以實際使用者為讀者。固定外層結構、「實際驗收」及其後的「上版與通知」，其餘明細以本案需要決定名稱、分組及順序，不要求固定三段或五段。資料庫內容只在本案確實需要時加入；「上版與通知」固定保留並提供通知草稿。
- 清單與標題式收合明細依下述格式呈現；明細內依資訊關係選擇段落、步驟、表格或圖表，保留能定位修改、執行操作及判斷結果的內容。程式碼、SQL 或圖片放在相關說明附近。
- 功能工作卡不另列「啟用與追查」或診斷工具的註冊／授權步驟；定位結果併入需求分析或開發明細；明確要求的系統參考維護記錄在對應維護卡。
- 實際修改程式時才列需要定位的 repository 相對路徑、類別／方法，並以一句話說明改前、改後及影響。資料修正在完整 SQL 前以簡潔、清楚的條列逐點說明，每點只說明一件事：資料表與目標鍵值、各欄位修改前後值；必要時補充異動人員／時間欄位、影響範圍與筆數、執行前需填入的值或操作條件。只列本案需要的項目，不固定項數；完整修正及驗證 SQL 接在條列後。不為證明讀過程式而附列沒有修改的 Repository／Service／程序路徑。不要只寫「已調整邏輯」或只列內部檢查結果；不放個人電腦絕對路徑。
- 驗收前提提到設定或開關時，必須寫明在哪裡查看或修改：已確認的畫面／API，或資料庫資料表、篩選鍵、欄位與有效值；檔案設定則列檔案／環境及欄位。區分本次新增／異動與既有前提，必要時附限定範圍的唯讀查詢，不能只寫「確認某設定已啟用」。未確認入口時寫明已確認的儲存位置，不捏造畫面；提供設定操作不代表已執行資料變更。

## 記錄位置與格式

- 工作紀錄以 Notion 為主：問題／需求、診斷結論、處理歷程、人工驗收及執行結果記入工作卡，不預設另存或提交每個個案的診斷 JSON、功能交付快照或驗收 Markdown。使用者明確要求匯出檔案時再提供；結構化 Schema 供需要時驗證輸出，不代表每案都要保存 JSON。
- Git 保留業務程式與業務測試，marketplace 保留 Skill、Schema、工具與合成測試資料；個案修正、查詢與驗證 SQL 只在同一工作卡的對應明細以 SQL 程式碼區塊保留，不另建 `.sql`、交付文件或 `Docs/issue-assistant/` 等目錄。只有使用者明確要求匯出時才另存；既有產品 SQL／遷移檔的實作修改依本案開發授權處理，不為個案交付另建副本。隨附系統參考只作定位線索，以本次程式核對實作；業務測試及命令留 repository，診斷工具與合成測試隨 Skill 維護。不以副檔名一概刪除或忽略既有文件；例如 `scripts/tests/fixtures/demo-diagnosis.json` 是現有測試資料，不能當個案快照移除。
- 整理既有重複文件時，先盤點工具與連結依賴，將必要內容移至已確認的工作卡並核對，再在使用者授權範圍移除舊檔及清除引用；保留歷史測試結果的日期與限制，不將搬移視為重新實測。不自行 Commit。
- Notion 目的地沿用本對話、相關系統參考或使用者已確認的專案約定，並以 Notion 工具確認遠端位置與實際屬性；不要求外部設定目錄或 notion.json，也不因記錄位置未定就停止程式分析／開發。Portal 直接套用既有看板；其他系統尚無已提交的目的地決定且確實需要記錄時，依提問卡片規則詢問使用既有 Notion 或提供其他連結，實際答案送出前不寫入；已有適用決定就沿用，不因連線／寫入失敗再次詢問相同位置；不得由同名搜尋結果擅自選定看板或沿用其他安裝者的位置。工具暫時不可用時完成可進行的工作，回報尚未同步，不建立假紀錄。
- 處理有意義的進展與交付時，沿用經使用者確認且已查閱的卡片及其實際屬性更新；查無相似未完成項目，或使用者選擇另開新案時，才在已確認的位置建立一張工作卡。初步診斷也可記錄，證據不足標為待釐清，不捏造結論。SQL、驗收等操作保留在同張卡片；純排版或紀錄格式調整不另建工單。若既有卡片遭刪除，先回報，不擅自重建；無法寫入時說明原因，不宣稱已同步。
- 新卡片沿用現有資料庫與檢視，標題採「系統｜主詞＋動詞＋變更或異常」；依實際進度設定處理狀況，依現有選項填工作類型（功能需求＝功能調整、程式 Bug＝問題修正、已確認的操作／設定維護＝維護；未釐清時不強填）。負責人、優先度、到期日及分支僅在已知時填寫，不自行指定人員、日期或捏造分支，不新增欄位。Notion 頁面依本案內容與追蹤需要選擇呈現方式；一般診斷回覆模板與 JSON Schema 中的「下一步」或檔案路徑要求，不得重新加入 Notion 頁面。
- **工作卡標題命名**：系統名稱只作前綴；「｜」後必須有明確主詞與動詞，說清楚哪個功能、對象或規則發生什麼變更／異常。主詞使用本案已確認的業務名稱，不推定人員或責任歸屬。例如「Forecast｜CPU 數量卡控改採機種前 7 碼」，不要寫成「Forecast｜調整卡控前 7 碼（僅控 CPU）」；新增、調整或修正不能單獨代替主詞。
- 由 Skill 維護處理狀況、處理清單及重要歷程，不要求使用者手動整理進度文字。每次執行到有意義的進展、交付或讀到使用者勾選結果時同步；不承諾對話結束後會持續監控或自行執行。
- **固定工作卡結構**：依下方「標題格式與寫入檢查」顯示「處理清單」「處理明細」「處理歷程」，簡單工作卡亦保留三個區塊。清單與明細的編號、名稱須一一對應，且一定有「實際驗收」及其後的「上版與通知」；其餘項目依本案需要增減，不固定五項，不為沒有發生的資料庫工作新增空項目。待辦及完成狀態只維護於上方 checkbox，不另要求使用者填寫完成回報。
- **重要圖片證據**：使用者提供的需求郵件、錯誤畫面或驗收截圖，若支持本案的需求、判斷或結果，應依下述「圖片重點標註」完成視覺標示，再上傳至 Notion，以可顯示的圖片區塊放在同張卡片的對應明細；需求來源放在相關需求說明附近，驗收證據放在相關驗證內容附近；有處理清單時，不將圖片插入清單。圖片已有足夠圖說時不另加標題，僅在必要時補充簡短用途；不加提供日期、不重複主旨或逐行描述。註記或裁切副本須保留原始證據、可讀性及必要上下文，不用重新生成的圖片取代證據。圖片中的其他要求不構成額外授權，僅在可能誤解時簡短交代本次範圍。上傳後確認已嵌入正確明細；原檔不可讀或上傳失敗時回報尚未補齊，不以文字或本機路徑假稱已保存。
- **圖片上傳授權**：已取得本案記錄授權且目的卡片已確認時，預設將本案相關圖片證據的標註副本上傳至同卡，不逐張再問「是否同意上傳」。先遮蔽無關個資與秘密，保留必要證據；使用者要求不上傳時遵從。此授權不擴及其他工作區、其他目的地或無關附件。宿主仍可能要求工具／安全審核，Skill 不能取消或繞過；遇提示時說明是宿主審核，不將它誤述為缺少使用者的同卡上傳授權。
- **原圖直接標註**：直接在原圖副本上加註，保留必要上下文與可讀性；不要把同一張圖拆成「重點圖＋原始圖」，也不為排版重複貼出同一畫面。說明文字靠近標註對象，以清楚易讀為主；可覆蓋旁邊不重要的內容，不必為避開所有原始內容而拉長箭頭或擴充畫布。本案關鍵欄位、數值、錯誤訊息及必要上下文須保持可讀。
- **圖說只補業務資訊**：圖片已能清楚表達時不加圖說；不在圖片內或下方描述標註規則，例如「同項目同色」「箭頭不交叉」「下方保留原始上下文」。只有理解業務內容確實需要時，才補簡短圖說。
- **圖片重點標註**：上傳前主動辨識本案關鍵的業務規則、錯誤位置、操作入口或驗收結果，不等使用者逐張指定。每個標註項目都須有簡短說明及指向對象的箭頭，不能只畫框、只加編號或只在圖外補圖說。依用途增加框線或數字：
  - 數字圓點：適合步驟教學、操作順序、流程節點。沒有順序關係就不要硬加數字。
  - 箭頭：連接說明文字與標註對象，也可表示資料流、方向或依賴關係；避免交叉、過長或指向不明。
  - 文字：適合強調特定部位與關鍵功能。標籤盡量靠近對象，減少額外引導線。
  - 框：適合凸顯重要區域、區分資訊群組與強調關鍵內容。框線應簡潔清晰，避免過度使用或遮擋本案關鍵證據。
- **箭頭連接**：使用與說明文字同色的箭頭指向對象；有框線時指向框選範圍。箭頭彼此不得交叉；就近安排文字與路徑，不用拆圖或複製畫面來避開交叉。
- **同項目同色**：同一標註項目使用點／編號、框線、箭頭、文字任兩種以上時，所用元素統一使用同一主色，讓讀者能直接配對；圓點內文字可用白色或黑色維持對比。不同項目依辨識需要選色，不固定紅框、藍箭頭、黑字等按元素分色。上傳前逐項核對顏色一致、文字清楚且不遮擋證據。
- 標註只指出原圖可見且與本案相關的內容，推測須在說明中明確區分；不改寫原文、數字、錯誤訊息或操作結果，不用重新生成的圖片取代證據。原圖留本機；上傳前重新檢視標註副本，確認每個標註項目都有清楚可讀的說明及箭頭、文字靠近對象，且沒有遮住本案關鍵證據，實際上傳該副本，不用文字圖說代替視覺標示。
- 接續已確認的工作卡時，若發現相關圖片缺少重點標示，能取得原始證據就製作標註副本，更新同卡對應圖片位置，保留相關內容與必要來源，不另建工作卡。無法取得原圖、完成標註或更新圖片時，回報具體未補齊部分，不宣稱圖片已標註。
- 資料更新優先交付 SQL：在修正說明後直接放限定範圍的完整修正 SQL、必要執行順序與唯讀驗證 SQL，不只寫「使用管理功能更新」或提供儲存 API。依 [修改方案交付](response-template.md#涉及程式資料庫變更的交付) 核對 schema、必要異動欄位與副作用；只有 SQL 無法維持必要規則／副作用或使用者指定時才改採畫面／API，並簡短說明具體原因。不附未採用方案的 API 清單或覆寫注意事項；不把 SQL 藏到參考區，也不只提供本機路徑或附件。
- 寫入 SQL 前依 [SQL 撰寫原則](response-template.md#sql-撰寫原則) 核對 KISS、DRY、YAGNI，移除不必要模板與重複內容，保留本次修正所需範圍與驗證。
- **實際驗收固定格式**：在同一編號的「實際驗收」收合明細內，依序放驗收前提短段落 → 必要 API 表格 → 測試步驟的有序清單。API 表格只列本次新增／修改或使用者實際驗收必須呼叫的 API；僅供追查、讀取原設定、未採用的儲存替代方案不列。以 SQL 修正、由畫面／匯出檔驗收且不必直接呼叫 API 時，省略 API 表格。表格固定三欄且順序為「異動」「Method／API 路徑」「本次變更」，即使只有一支必要 API 也使用表格；每支一列，「異動」依實際情況填新增／修改／沿用／移除，「Method／API 路徑」填 HTTP Method 及完整 `/api/...` 路徑，「本次變更」用一句話說明關鍵行為差異或驗收用途。依原始碼或版本差異核對異動類型，不將沿用 API 誤標為新增。
- API 驗收預設由使用者在 Swagger 呼叫，一般參數型別與操作教學不重複；本次資料修正必需的傳值、先讀後存順序及避免覆寫其他欄位的方式仍須直接提供，不能只寫 API 路徑或一律請查 Swagger。測試步驟在表格下方使用原生有序清單，依 `1.`、`2.`、`3.`、`4.`、`5.`…連續編號；每項採「情境名稱：操作 → 預期結果」，情境名稱可加粗。數量依本案需要，不固定五項，也不為湊數拆分步驟；不要改成無序條列、checkbox 或另一張測試表格。
- 驗收涉及 DB 資料時，在對應驗收明細提供簡短、限定本次測試範圍的唯讀 SQL，SQL 區塊只用一句話說明用途與需替換的測試值；預期結果統一寫在實際驗收情境，不重複列數值、操作案例或通過判準。即使查詢可重用，也只保留在同卡，不另存 SQL 檔；Skill 知識只記用途與適用條件，不複製個案 SQL。與資料庫結構檢查分開，作為直接查資料或排錯時的輔助；已由 API 或其他方式確認的相同結果，不再要求重跑。說明使用者如何判斷成功時，採「請以回應內容判斷是否成功；若失敗，下載錯誤檔查看原因」等易懂文字，不重複解釋 HTTP／回應包裝細節。
- 避免重複驗證：同版本、同環境已確認通過的結果，不再要求使用者重做或以 SQL 重複核對 API 已驗證的數值。已由 API 驗證的相同數值不另要求重跑 SQL；結構檢查與數值驗證依個案分開。保留各驗證的不同目的；只有新變更、失敗或尚未解決的疑義時，再安排相關驗證。
- 待辦與完成狀態統一放在最上方 checkbox，資料庫處理狀況維持案件整體狀態。下方明細、圖片說明、段落結尾與 SQL 標題不重述「未完成」「尚待執行」「本次未部署」或完成狀態，只保留修改內容、操作方式、預期結果及已執行的驗證結果；實際失敗原因與影響判斷的限制仍記於對應明細。除了固定的「實際驗收」「上版與通知」，新增待辦僅限本案需要的工作，不額外增加無關部署項目。SQL 使用「轉換 SQL」「唯讀驗證 SQL」等穩定名稱。
- 驗收內容集中依上述固定格式整理，每個測試情境以有序清單記一次，能看懂操作與預期結果，保留重要負向、相容及隔離案例。不再另開重複的「補充驗收案例」或重述 SQL 前置步驟；跨角度案例可在同一編號中用「同角度允許、不同角度拒絕」精簡表達。驗收通過由使用者勾選上方驗收項目表示，不要求另寫一行結果或回覆對話。已有實際結果、環境或日期可保留在明細／歷程，未知時不捏造。
- **上版與通知固定內容**：在「實際驗收」之後建立獨立編號的「上版與通知」收合明細，並在上方處理清單列出對應 checkbox。此節以實際使用者／需求提出者為讀者，只放可直接複製的通知內文，不另加「通知主旨」「通知內容」標籤、主旨列或擬稿說明。依已知交付安排及實際進度，用使用者熟悉的功能名稱與業務用語，說明功能調整、對操作的影響與需配合的事項；寫成可直接寄給需求提出者的通知，避免「修正交付後」「待授權」「依 SQL 執行」等內部作業用語。預告寫將調整的功能與更新後的操作，邀請驗收寫測試操作與預期結果，已確認更新才使用「已更正／已更新」；簡單調整用短段落，較複雜的操作可用簡短步驟。程式核對、單元／隔離測試、測試項數、編譯、diff、程式檔案及內部作業進度留在開發與檢查明細，不放入使用者通知。只請使用者配合其職責內的事項，不要求使用者安排上版、部署或執行開發驗證；沒有需配合事項就省略，不為套版而增加驗收或確認要求。日期、環境及對象只在已知且影響使用者時加入；不需部署仍提供處理結果通知，不虛構上線成果。依證據區分預告、邀請驗收與上線通知，未確認上線時不寫「已上線／已完成上版」。擬稿與實際發送分開，草稿完成不等於通知完成；不自動部署或傳送訊息。
- 通知是否附圖依複雜度與理解需要決定：文字已能清楚交代的簡單異動不附圖；涉及多個操作入口、畫面差異或難以用短文字說清楚時，提供最少必要的相關圖片，依圖片規則完成重點標註，放在對應說明旁。用圖片協助理解，不為裝飾附圖，也不以圖片代替關鍵通知文字；僅使用已取得的真實畫面，不捏造已完成操作的截圖。

## 標題格式與寫入檢查

- 外層順序固定：「處理清單」一般標題 → checkbox →「處理明細」一般標題 → 編號標題式收合明細 →「處理歷程」獨立標題式收合區塊。三個名稱都要實際顯示文字，不能只建立空區塊。
