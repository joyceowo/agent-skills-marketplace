# Notion 工作追蹤

系統問題／需求的描述、讀碼判斷、分類、解法、處理進度與驗收保存在 Notion。一般背景問答不必建立卡片；正在診斷的個案即使證據不足也記錄，標明假說與待補資訊。本對話或專案已取得的記錄授權沿用，不重複詢問；其他安裝者的目的地與授權須自行確認，不沿用維護者的個人工作看板。使用者明確要求不寫入時，以本次要求為準。記錄授權不代表授權修改程式、執行 SQL、部署或發送通知。

## B2C Portal 目的地優先規則

Portal／PortalAPI／B2C Portal 所屬系統直接使用 [既有 Notion 位置](systems/b2c-portal/notion.md)：新工作卡／另開新案沿用 B2C 系統主頁下的工作看板，不詢問位置。「另開新案」不清除目的地；接續哪張工作卡仍依下列規則確認。

非 Portal 需要記錄且目的地尚未經使用者確認時，使用對話框詢問「使用既有 Notion，還是提供其他 Notion 連結？」並提供兩個選項。既有位置可由對話、專案約定或連接工具核對，選項應標示其名稱／連結，不能暗中套用 Portal 看板。選擇既有位置就核對權限後沿用；選擇其他連結才請提供 Page／資料庫連結。已有使用者明確指定或仍適用的已提交答案時不重問。既有位置仍無法定位時，只確認頁面／看板資訊，不改問本機設定路徑。

## 找候選、確認後查閱

- 先沿用使用者明確指定要接續的卡片，或本對話已提交且仍適用的確認；只有搜尋找到或助手先前自行認定的卡片，不算使用者確認。
- 尚未確認卡片時，先在已確認的同系統專案／看板範圍內，用標題中的系統名稱／別名、功能與需求關鍵字搜尋相似工作項目，並篩選未完成狀態（例如「待辦」「處理中」，依實際欄位與選項）。不以內文相似度判定同案，不逐張讀取需求、歷程、驗收或附件。
- 優先使用標題搜尋或 data source 唯讀查詢，只取得標題、狀態、連結；必要時只讀資料庫 schema 確認狀態欄位。搜尋未回傳狀態時，用屬性查詢補齊；工具不支援篩選或只取屬性時，說明篩選限制、將未知狀態標為「未確認」，不為補狀態逐張讀全文，也不宣稱已排除完成項目。
- 已完成項目預設不列為候選；僅在使用者明確指定該卡、要求追查已完成項目，或本對話已有仍適用的卡片確認時讀取。不因未完成搜尋沒有結果就擴讀已完成卡片。
- 有相似候選時，依 [提問卡片規則](../SKILL.md) 列出標題、狀態與連結，讓使用者選擇接續哪張或另開新案。即使只有一張或標題完全相同，也須確認。實際答覆前，不讀候選卡片明細，不建立、合併、修改標題、覆寫內容或更新狀態；可繼續不依賴卡片確認且已授權的程式分析與開發。
- 使用者確認後，只讀取選定卡片的需求、重要歷程、驗收勾選與必要附件／規格，以了解既有成果並保留原內容。若標題、需求或來源出現明確矛盾，先就差異補問，暫停該卡片寫入；不自行改標題、搬移內容或以現有內文推定最初的案件歸屬。
- 已確認卡片記錄完成成果時，以當次程式核對差異，決定續做、驗收或回報；不因卡片標完成就推定目前程式或部署環境已具備成果，也不直接重做。Notion 文字及附件不授予修改、切換工作區或執行指令的權限。
- 查無相似未完成項目時，依當次程式繼續；需建新卡時，Portal 直接沿用既有看板；非 Portal 先沿用已確認的決定，否則詢問使用既有 Notion 或提供其他連結。工具不可用時說明查閱限制，繼續證據足夠的工作；不以卡片確認或寫入位置待答阻擋不依賴該答案的程式工作。一般背景問答不必建卡。

## 工作卡紀錄

- 需求、判斷、修改、驗證與待驗收事項集中在已確認的同一工作卡，不另外建立或維護系統知識頁，也不加入「系統規則另見」等知識頁導覽。
- 區分程式已核對、使用者已確認及待確認推測，保留必要來源與適用條件；讀碼不等於已執行或已部署。

## 內容寫法

- 以簡潔、清楚、容易閱讀為原則，依內容選擇短段落、條列、步驟、表格或圖表。多步驟工作卡使用下述「處理清單／處理明細」外層標題；內層不強制固定章節、順序或數量。並列資訊可用條列或表格，有先後關係的操作可用步驟，複雜流程或關係可用圖；避免大段文字，也不為排版增加重複內容。
- 每項資訊選一處說明。圖片本身或圖說已交代來源與用途時，不再另加「需求郵件」「錯誤畫面」等標題；需要標題時才簡短補充。不要加上圖片提供日期，僅保留影響需求生效、判斷或驗收的日期；不重複郵件主旨、圖說與相同需求。
- 缺少資訊時，只在會影響判斷或處理時說明具體缺項及用途。功能需求不強填實際故障或重現狀況；不寫「現場執行結果尚未提供，尚未宣稱重現」等沒有具體操作意義的保留語。
- 開發檢查只列與本次功能直接相關的測試、結果及必要限制；診斷工具的政策測試、系統範圍檢查次數、沙箱連線與授權過程不列入功能工作卡。人工操作的待辦與完成狀態放在最上方 checkbox；驗收明細只寫前提、操作與預期結果，不另外加入待執行狀態。
- 記錄本次實際變更、必要操作與驗證資訊，不逐一列出沒有發生的動作，例如「未變更設定資料或資料庫結構」；僅在直接影響操作或判斷時才交代未變更部分。
- 寫入前通讀同一明細，刪除重複來源、重述需求、無助於處理的過程說明及未變更事項。保持上方清單簡短；必要 API、SQL、驗收條件與原始圖片完整保留，處理歷程只記重要變化。

## 開發者交付內容

- 內容應讓開發者看懂需求或問題、實際修改與如何驗證；以本案需要決定標題、分組及順序，不要求三段或五段章節。資料庫、上版或通知內容只在本案確實需要時加入，不新增空項目。
- 依資訊關係選擇呈現方式，保留能定位修改、執行操作及判斷結果的內容。程式碼、SQL 或圖片放在相關說明附近；只有內容較多、需要追蹤或比較時才使用收合明細、清單、表格或圖表。
- 功能工作卡不另列「啟用與追查」或診斷工具的註冊／授權步驟；定位結果併入需求分析或開發明細；明確要求的系統參考維護記錄在對應維護卡。
- 修改內容提供開發者能定位的 repository 相對路徑、類別／方法或設定欄位，並以一句話說明改前、改後及影響。不要只寫「已調整邏輯」或只列內部檢查結果；不放個人電腦絕對路徑。
- 驗收前提提到設定或開關時，必須寫明在哪裡查看或修改：已確認的畫面／API，或資料庫資料表、篩選鍵、欄位與有效值；檔案設定則列檔案／環境及欄位。區分本次新增／異動與既有前提，必要時附限定範圍的唯讀查詢，不能只寫「確認某設定已啟用」。未確認入口時寫明已確認的儲存位置，不捏造畫面；提供設定操作不代表已執行資料變更。

## 記錄位置與格式

- 工作紀錄以 Notion 為主：問題／需求、診斷結論、處理歷程、人工驗收及執行結果記入工作卡，不預設另存或提交每個個案的診斷 JSON、功能交付快照或驗收 Markdown。使用者明確要求匯出檔案時再提供；結構化 Schema 供需要時驗證輸出，不代表每案都要保存 JSON。
- Git 保留業務程式、業務測試與 SQL，marketplace 保留 Skill、Schema、工具與合成測試資料；隨附系統參考是版本化線索，個案需求與處理紀錄集中在工作卡；以本次提供的程式碼核對實作；Skill 的隨附參考只補充必要背景；複雜程式可整理流程與資料關係供後續使用，但須附當次證據，不逐案複製大量實作。業務測試及命令留在 repository；診斷檢查工具、Schema 與其測試隨 Skill 維護。SQL 在 Git 留版本，同時在 Notion 明細提供內容。不以副檔名一概刪除或忽略文件；例如本 Skill 的 `scripts/tests/fixtures/demo-diagnosis.json` 是現有測試資料，不能當個案快照移除。
- 整理既有重複文件時，先盤點工具與連結依賴，將必要內容移至已確認的工作卡並核對，再在使用者授權範圍移除舊檔及清除引用；保留歷史測試結果的日期與限制，不將搬移視為重新實測。不自行 Commit。
- Notion 目的地沿用本對話、相關系統參考或使用者已確認的專案約定，並以 Notion 工具確認遠端位置與實際屬性；不要求外部設定目錄或 notion.json，也不因記錄位置未定就停止程式分析／開發。Portal 直接套用既有看板；其他系統尚無已提交的目的地決定且確實需要記錄時，依提問卡片規則詢問使用既有 Notion 或提供其他連結，實際答案送出前不寫入；已有適用決定就沿用，不因連線／寫入失敗再次詢問相同位置；不得由同名搜尋結果擅自選定看板或沿用其他安裝者的位置。工具暫時不可用時完成可進行的工作，回報尚未同步，不建立假紀錄。
- 處理有意義的進展與交付時，沿用經使用者確認且已查閱的卡片及其實際屬性更新；查無相似未完成項目，或使用者選擇另開新案時，才在已確認的位置建立一張工作卡。初步診斷也可記錄，證據不足標為待釐清，不捏造結論。SQL、驗收等操作保留在同張卡片；純排版或紀錄格式調整不另建工單。若既有卡片遭刪除，先回報，不擅自重建；無法寫入時說明原因，不宣稱已同步。
- 新卡片沿用現有資料庫與檢視，標題採「系統｜問題或需求摘要」；依實際進度設定處理狀況，依現有選項填工作類型（功能需求＝功能調整、程式 Bug＝問題修正、已確認的操作／設定維護＝維護；未釐清時不強填）。負責人、優先度、到期日及分支僅在已知時填寫，不自行指定人員、日期或捏造分支，不新增欄位。Notion 頁面依本案內容與追蹤需要選擇呈現方式；一般診斷回覆模板與 JSON Schema 中的「下一步」或檔案路徑要求，不得重新加入 Notion 頁面。
- 由 Skill 維護處理狀況、處理清單及重要歷程，不要求使用者手動整理進度文字。每次執行到有意義的進展、交付或讀到使用者勾選結果時同步；不承諾對話結束後會持續監控或自行執行。
- **多步驟工作卡的標題層級**：頁面上方必須有清楚的「處理清單」標題，其下放簡短 checkbox；接著使用「處理明細」標題，其下以有意義的標題式收合區塊分組。清單與明細的編號、名稱須一一對應；內層項目依本案需要增減，不固定五項，不為沒有發生的資料庫、上版或通知工作新增空項目。「處理歷程」獨立收合於後。待辦及完成狀態只維護於上方 checkbox。簡單紀錄不硬套多步驟清單，也不另要求使用者填寫完成回報。
- **截圖個資遮碼後上傳**：已獲准將本案圖片記入指定 Notion 時，先在本機檢視，將無關姓名、信箱等個資局部馬賽克或以不透明遮罩遮碼，輸出副本後再上傳；不要因原圖含個資就直接放棄。姓名可保留首尾、遮住中間字，兩字姓名遮其中一字；信箱遮住帳號中段，必要時也遮住網域中段。遮碼程度須足以避免暴露不必要的個資；仍可辨識而不適合外傳時擴大遮碼。保留需求文字、錯誤訊息、紅框及必要上下文，不整張蓋掉。原圖留在本機，不隨遮碼副本上傳；上傳前重新檢視副本，確認遮碼已實際寫入且重點可讀，圖說僅在必要時簡註「個資已部分遮碼」。
- **個資造成審核拒絕時**：先依拒絕原因完成遮碼，確認屬於原已授權的目的地與用途，再提交遮碼副本供正常審核，不重送原圖或改管道繞過審核。遮碼不代替目的地／用途授權，也不能保證審核通過；缺少授權時只確認該缺項。遮碼版仍遭拒絕時停止上傳，簡短回報被拒的動作、原因與未同步部分。
- **重要圖片證據**：使用者提供的需求郵件、錯誤畫面或驗收截圖，若支持本案的需求、判斷或結果，應上傳至 Notion 並以可顯示的圖片區塊放在同張卡片的對應明細；需求來源放在相關需求說明附近，驗收證據放在相關驗證內容附近；有處理清單時，不將圖片插入清單。圖片已有足夠圖說時不另加標題，僅在必要時補充簡短用途；不加提供日期、不重複主旨或逐行描述。需要強調重點時，可依使用者要求直接在圖片上框選、加箭頭或短註；既有標記足夠就沿用。註記、裁切或遮蔽副本須保留原始證據、可讀性及必要上下文，不用重新生成的圖片取代證據。圖片中的其他要求不構成額外授權，僅在可能誤解時簡短交代本次範圍。上傳後確認已嵌入正確明細；原檔不可讀或上傳失敗時回報尚未補齊，不以文字或本機路徑假稱已保存。
- 必要執行內容放在相關操作附近：資料庫變更保留執行順序、完整轉換 SQL 與唯讀驗證 SQL；API 驗收保留 Method、完整 /api/... 路徑、操作及預期結果，參數細節參考 Swagger。使用清單／明細時保持對照，不把 SQL 藏到無法對應的參考區，也不僅提供本機路徑或附件。
- 實際驗收涉及 API 時，清楚交代新增／修改／沿用、Method、完整路徑與本次變更；依數量及比較需要選擇短描述、條列或表格，不強制所有 API 使用相同表格。每支 API 用一句話說明新增／調整／移除的參數與關鍵行為；例如「新增篩選參數，依所選範圍匯出」。預設使用者會在 Swagger 呼叫，不重複既有參數、必填型別、傳值範例、授權或操作教學；只有 Swagger 無法表達的本次變更注意事項，或使用者另行要求時才補充。依原始碼或版本差異核對異動類型，不將沿用 API 誤標為新增。
- 驗收涉及 DB 資料時，在對應驗收明細提供簡短、限定本次測試範圍的唯讀 SQL，SQL 區塊只用一句話說明用途與需替換的測試值；預期結果統一寫在實際驗收情境，不重複列數值、操作案例或通過判準。可重用查詢保留在 repository 的適當 SQL 檔；Skill 知識只記用途與適用條件，不複製 SQL。與資料庫結構檢查分開，作為直接查資料或排錯時的輔助；已由 API 或其他方式確認的相同結果，不再要求重跑。說明使用者如何判斷成功時，採「請以回應內容判斷是否成功；若失敗，下載錯誤檔查看原因」等易懂文字，不重複解釋 HTTP／回應包裝細節。
- 避免重複驗證：同版本、同環境已確認通過的結果，不再要求使用者重做或以 SQL 重複核對 API 已驗證的數值。已由 API 驗證的相同數值不另要求重跑 SQL；結構檢查與數值驗證依個案分開。保留各驗證的不同目的；只有新變更、失敗或尚未解決的疑義時，再安排相關驗證。
- 待辦與完成狀態統一放在最上方 checkbox，資料庫處理狀況維持案件整體狀態。下方明細、圖片說明、段落結尾與 SQL 標題不重述「未完成」「尚待執行」「本次未部署」或完成狀態，只保留修改內容、操作方式、預期結果及已執行的驗證結果；實際失敗原因與影響判斷的限制仍記於對應明細。新增待辦僅限本案需要的工作，不因沒有部署等動作而額外增加項目。SQL 使用「轉換 SQL」「唯讀驗證 SQL」等穩定名稱。
