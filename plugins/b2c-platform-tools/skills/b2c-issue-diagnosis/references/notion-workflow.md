# Notion 工作追蹤

## 目的地與工作卡

- 沿用使用者已指定的目的地與卡片。Portal 依 [既有看板解析](systems/b2c-portal/notion.md)，新案也沿用同一看板；非 Portal 需記錄且位置未確認時，提問提供「使用既有 Notion」「提供其他 Notion 連結」，列出可核對的既有位置，選其他後才請提供連結。
- 尚無選定卡片時，在同系統範圍以標題關鍵字及未完成狀態搜尋，只取標題、狀態、連結。缺狀態用屬性查詢補齊；無法取得就標未確認，不逐張讀全文，也不宣稱已排除完成項目。
- 找到候選即請使用者選接續哪張或另開新案；只有一張或同名也不能自行認定。已完成卡片只在使用者指定／要求追查時讀取；沒有候選才按本次需求建新卡。一般問答不必建卡。
- 確認後讀選定卡片的需求、歷史、驗收與必要附件，再局部更新同卡。保留人工勾選與歷史；歸屬／需求有矛盾時補問差異，不改標題掩蓋問題。卡片被刪除或失去存取時先回報，不擅自重建或換目的地。
- 新卡沿用現有 schema、欄位及選項，不增欄位。標題用「系統｜主詞＋動詞＋變更或異常」，例如「Forecast｜CPU 數量卡控改採機種前 7 碼」。依實際進度填狀態與工作類型；負責人、日期、分支未知就不填，分支已知時保留完整名稱。

記錄授權沿用本案已確認決定，使用者要求不寫入時遵從。遠端權限、目的卡確認與其他操作授權各自成立；失敗不清除原決定。只將必要需求、修正與驗收留同卡，不額外建立知識頁。內容取捨及 SQL 交付依 [交付規則](response-template.md)。

## 結構與進度

外層依序保留：

1. 「處理清單」一般標題及 checkbox。
2. 「處理明細」一般標題及標題式收合明細；用 `01｜名稱`、`02｜名稱` 連續編號，清單與明細一一對應。項目依本案增減，必須有獨立的「實際驗收」及其後的「上版與通知」，不固定五項，也不加空的資料庫／部署工作。
3. 「處理歷程」獨立收合標題；以使用者時區的實際六碼日期 `YYMMDD：內容`，新到舊、同日新紀錄在前，每筆一兩句，不用日期 mention。舊日期可確認才轉換，不捏造相對日期。

待辦與完成狀態只列在頂端 checkbox；明細保留實際修改、操作、預期與已取得結果，不重述待執行狀態。人工驗收勾選／狀態可作使用者確認，下次讀取時沿用，不當成工具實測；不要求另回覆一次，也不承諾背景監控。只有 Skill 工作與人工項目均完成才結案。

## 文字重點用色

主動用 Notion **原生文字顏色**標出重要差異及條件，不能只靠粗體或 SQL 語法高亮：修改前／錯誤值用紅色，修改後／目標值用綠色，執行範圍與必要條件用橘色。只著色關鍵詞與數值，不整段染色；同義用色保持一致，避免把目標值綠色誤寫成已驗證完成。

Notion Markdown 用 `<span color="red">文字</span>` 等支援色彩，原生 API 用對應 rich text 的 `annotations.color`。不要使用 CSS、`<mark>` 或把標籤放進 SQL／行內程式碼裡。

```markdown
- 將平台由 <span color="red">原錯誤值</span> 改為 <span color="green">目標值</span>。
- 僅處理 <span color="orange">本次已確認的週別與料號</span>。
```

這些是格式示例，不是可套用的業務值。寫入後核對顏色是否保存；工具只回純文字時，進一步讀取區塊格式或實際頁面確認，不能用「寫入成功」推定重點已上色。

## 圖片標註與上傳

- 有本案記錄授權且卡片已確認時，相關需求郵件／錯誤／驗收圖片標註後直接上傳同卡，不逐張再問。使用者要求不上傳時遵從；宿主工具審核仍依實際限制處理，不擴及其他目的地或無關附件。
- **不預設遮碼圖片中的姓名、帳號、聯絡資訊等個人資訊**；只有使用者要求時才遮碼。登入憑證與秘密的處理依 [存取規則](data-log-access.md#秘密與連線取用)，不把個人資訊遮碼當成一般上傳前提。
- 在單張原圖副本上直接標註，保留原圖；不拆成「重點圖＋原始圖」或重複貼圖。每個需補標的重點使用簡短說明及指向對象的箭頭，框線／數字按需增加；已有足夠標記時沿用。
- 同項目的文字、箭頭、框線及編號同一主色，圓點內字可用黑／白保持對比。文字靠近對象、箭頭不交叉；可覆蓋不重要內容，但關鍵欄位、數值、錯誤及上下文必須可讀。數字只用於順序／流程，不為裝飾增加元素。
- 不改寫原文或用生成圖片取代證據。上傳前檢視實際副本的指向、顏色與可讀性，實際上傳該副本；圖片緊接相關來源、需求或驗收文字，以獨立圖片區塊呈現，不另開圖片章節／清單項目。
- 來源只交代一次；圖片已清楚就不加圖說，不加提供日期、重複主旨或製圖規則說明。取得／標註／上傳失敗在聊天回報具體缺項，不在卡片用工具過程代替圖片。既有同卡缺標註且可取得原圖時，局部補上，不重建整張卡。

## 實際驗收

依序放前提短段落、必要 API 表格、連續編號步驟。前提寫出設定入口／欄位及有效值；情境用 `1.`、`2.`…各寫「情境：操作 → 預期結果」，不另加重複案例或驗證相同數值。

API 表格固定為「異動」「Method／API 路徑」「本次變更」，只列本次新增／修改或驗收必須直接呼叫的 API；沿用時說明驗收用途。SQL 修正並以畫面／匯出檔驗收，不必列純追查讀過或未採用的 API。一般參數參考 Swagger，修正必需的具體傳值與防止整筆覆寫的做法仍須交代，見 [交付規則](response-template.md#涉及程式資料庫變更的交付)。

## 上版與通知

只放可直接寄給需求提出者的通知內文，以業務用語說明功能影響、操作變化與必要配合；沒有配合事項就省略。預告、邀請驗收或更新完成依實際進度措辭，不虛構上線；不需部署仍提供結果通知。

不加通知主旨／擬稿標籤、程式路徑、測試項數或「修正交付後／待授權／依 SQL 執行」等內部措辭，也不要求業務使用者安排部署。圖只在有助理解操作時附上，草稿完成不代表已發送。

## 寫入與核對

使用 Notion MCP 前，先讀取該連線的 `notion://docs/notion-flavored-markdown-spec`；同一規格已讀且適用時沿用。標題式收合的名稱必須是開啟標籤後的本文，與子內容間留一空行；原生 API 則用 `heading_2.rich_text`、`is_toggleable: true` 及 `children`，不以屬性或子段落代替標題。

以下只示範結構，明細名稱、數量及內容按本案調整：

```markdown
## 處理清單

- [ ] 01｜問題與修正
- [ ] 02｜實際驗收
- [ ] 03｜上版與通知

## 處理明細

<toggle heading="h2">
01｜問題與修正

問題、修改項目與本案核對的 SQL；圖片放在相關說明旁。
</toggle>

<toggle heading="h2">
02｜實際驗收

必要前提及 API 表格（需要時）。

1. 情境：操作 → 預期結果。
</toggle>

<toggle heading="h2">
03｜上版與通知

面向需求提出者、與實際進度一致的通知內文。
</toggle>

<toggle heading="h2">
處理歷程

以實際 YYMMDD 日期記錄重要變化。
</toggle>
```

寫入前後核對標題文字、編號／清單對應、必要驗收與通知、文字顏色及圖片位置。使用已儲存回傳內容確認；缺格式資訊、有警告或疑似空白／「Heading 2」標題時，再讀對應區塊或檢視頁面。局部修正並保留圖片、SQL、歷史及人工勾選，不重建整卡；仍無法確認就回報未完成的具體項目。
