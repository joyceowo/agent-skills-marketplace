# 診斷回覆格式
先辨識系統、查閱 Notion，再核對提供的程式碼；聊天回覆預設只保留簡短結論、實際處理狀態、必要的使用者動作與 Notion 工作卡連結。完整 SQL、查核依據、修改項目、測試及驗收步驟集中在同卡，不在聊天重貼；使用者明確要求展開或 Notion 無法同步時，才在對話提供必要細節。不要求 commit 或版本對照；系統參考只補充背景與定位資訊。

報告 Schema 用於需要結構化輸出時的驗證，不要求每個問題都另存 JSON。個案工作紀錄及修正、查詢與驗證 SQL 集中在同一 Notion 工作卡，不另產生 `.sql`、診斷 JSON、交付／驗收 Markdown 或其目錄。只有使用者明確要求匯出時才另存；業務程式、測試及既有產品 SQL／遷移檔的實作修改依本案開發授權處理。Notion 排版及人工結案方式依 [Notion 工作追蹤](notion-workflow.md)。

以下供診斷與 Notion 工作卡交付時檢查資訊是否完整，依本案需要選用，不要求在聊天逐欄填寫。Notion 工作卡採 [Notion 工作追蹤](notion-workflow.md) 的簡潔寫法，不照抄分類代碼、保留語或不適用欄位。

每段都檢查：刪除後是否影響根因判斷、修改範圍、執行或驗收？不影響就省略。預設用簡短問題與結論、具體修正、必要驗收交代，不把內部追查紀錄當成報告內容。需要說明資料來源時，一句因果即可，不展開程序 → Repository → Service → Excel 的呼叫鏈、無關區域／關聯筆數或共同欄位清單。

以下是工作卡按需保留的資訊，不是聊天必備內容或固定章節；以簡潔、清楚、容易閱讀為原則，依內容選擇文字、條列、步驟、表格或圖表：
- 系統：名稱（system_id）
- 分類／影響：classification／impact_scope
- 結論與解法：直接說明如何處理、操作步驟或修改方案及預期結果；推測必須明講
- 預期／實際：依問題需要描述；缺少資料會影響判斷時，寫明具體缺項及用途。功能需求不強填實際故障或重現結果
- 證據：本次實際核對、足以支持判斷的最少結果；背景文件只作輔助，清楚區分已確認與推測。預設不附純讀取程式片段、行號或與修改無關的內部識別對照；必要操作鍵值與修正語法仍須保留。未執行時不說已重現，不聲稱來源已部署。
- DB／Storage 證據（實際查詢時）：用一句話交代正式／測試環境、查詢範圍、結果及其對結論的影響，資料列有助於判斷時才附精簡表格。主機／資料庫名稱、精確時間、時區補核及資源識別預設不放入回覆或工作卡，只有環境／時間差異影響判斷、重現所需或使用者明確要求時才補充。保留影響判斷的缺權限、截斷或保留期限等限制；連結移除秘密，零筆匹配不能推定沒有錯誤。
- 處理：可執行步驟、是否需要修改、是否已有授權
- 驗證：實際執行與結果；Notion 工作卡的待辦只列在最上方 checkbox，明細不另寫尚待執行或未完成。不可把設定檢查當作業務修復驗證
- 狀態：ANSWERED／NEEDS_INFO／PROPOSED_FIX／FIXED／OUT_OF_SCOPE
- 待補：會改變判斷的最少資料

只有需要結構化交付且已連接 repository 時，才使用本 Skill 的 [diagnosis.schema.json](schemas/diagnosis.schema.json) 與 `scripts/IssueAssistant.ps1 -WorkspaceRoot <目標工作區> -ScopeJson <本次分析的範圍JSON> -Action ValidateReport -ReportPath <工作區內相對路徑>`。工具與命令見 [程式碼診斷與修復](repository-workflow.md)。[示範 fixture](../scripts/tests/fixtures/demo-diagnosis.json) 僅供合約測試，不是實際個案證據。一般對話或 Notion 工作卡不強制產生 JSON。

只提供片段時直接以文字交付，不因片段無法通過 repository 報告路徑檢查而停止分析。

完整 JSON 不知道的文字欄寫「尚未確認」，未知清單用 []。尚無法辨識系統時 system_id、system_name 用空字串，classification=UNKNOWN、status=NEEDS_INFO，補問目標資訊；只有實際越出可存取／授權範圍才用 OUT_OF_SCOPE。未收錄系統不構成 OUT_OF_SCOPE。
尚未重現的程式風險用 PROPOSED_FIX／NEEDS_INFO，不能 FIXED。Test-Json 及輔助工具只能檢查格式與範圍，測試文字是否真實及根因是否正確仍由診斷者核對。

## SQL 撰寫原則

查詢、修正與驗證 SQL 均遵循：

- **KISS（保持簡單）**：使用足以完成本次需求的直接、易讀語句；只有實際需要時才加入變數、CTE、暫存表、動態 SQL 或額外控制流程，不為單次資料修正堆疊通用模板。
- **DRY（避免重複）**：重複使用且容易不一致的業務鍵、期間、目標值或條件，採簡單參數或適當共用方式維持一致；不重複相同查核，也不為消除少量重複而增加更複雜的抽象。更新前後驗證目的不同時，保留必要查詢。
- **YAGNI（只做目前需要的事）**：只涵蓋已確認的資料、欄位、期間及驗收，不預做未要求的歷史回補、批次能力、通用程序、新表或額外功能。

精簡以正確性與可讀性為前提，不省略必要的 WHERE 範圍、影響筆數檢查、異動欄位或唯讀驗證；交易與回復措施依實際風險保留。SQL 仍直接放在同一 Notion 工作卡，不額外產生檔案。

## 涉及程式／資料庫變更的交付

同一 Notion 工作卡應包含具體修改方式、已執行的驗證與可操作的驗收步驟。即使判定不必改程式，也要在卡片交付可照做的資料／設定修正；聊天僅摘要結論與實際處理狀態，附同卡連結，不重貼完整內容。

- **資料修正先列修改項目**：在 Notion 對應明細的 SQL 前，以簡潔、清楚的條列逐點說明，每點只說明一件事：資料表與目標鍵值、欄位修改前後值；依需要補充異動人員／時間、影響範圍與筆數、執行前需填值或條件。不以一大段文字取代條列，不固定項數，也不列不適用項目。
- **資料修正優先 SQL**：先核對當次原始碼與 schema，再提供限定業務鍵、期間及舊值的修正 SQL、影響筆數檢查與唯讀驗證 SQL；需要交易／回復方式時一併提供。核對必要異動時間／操作人欄位、約束與副作用，保留非目標欄位。在 Notion 對應明細的修正說明之後直接放完整 SQL 區塊，不能只給檔案路徑、建議使用管理畫面或列儲存 API。以已核對鍵值限定範圍，未知值清楚標示待填，不根據截圖猜資料表或欄位；必要資訊不足就先補核對。只準備腳本不需要取得 DB 寫入授權；實際執行寫入仍須另有明確授權。
- 畫面／API 修正僅作必要替代：只有直接 SQL 無法維持已核對的必要業務規則／副作用，或使用者指定時才採用；說明具體原因，不能因已有 API 就優先推薦。提供入口、Method／路徑、關鍵傳值及預期結果；若儲存會覆寫整筆或多筆資料，須交代先讀取並保留其餘欄位。已提供 SQL 且未採用 API 方案時，不再附列替代 API 清單或操作教學。
- 程式修正：指出實際檔案／方法、修改前後行為；已要求修復時完成修改與相關驗證。尚缺必要資訊時，提供已確定部分、具體缺項及取得方式，不交付猜測的可執行語法。

Notion 在對應處理明細以 SQL 程式碼區塊直接保留完整修正、查詢與驗證語法、用途及執行順序，不另存本機檔案；聊天只摘要結論、實際處理狀態及必要的使用者動作，附同卡連結。Notion 無法寫入時，在對話提供 SQL 並回報未同步，不以另存檔案作為備援，也不宣稱已保存。依變更需要補充下列資訊，不將單純問答膨脹成部署清單：

| 交付項目 | 應提供的內容 |
| --- | --- |
| SQL 內容 | 同一 Notion 工作卡內可直接複製的完整修正與驗證 SQL、各段用途與執行順序，不另產生檔案或要求檔案路徑；執行狀態只列在最上方 checkbox；註解與自訂提示預設繁體中文 |
| 環境與前提 | 測試資料庫／測試 API、先套 DB 再啟動新版程式等必要順序；未知的位址、帳號與測試資料標示須替換 |
| 設定位置 | 設定的畫面／API，或資料表、篩選鍵、欄位及有效值；檔案設定列檔案／環境與欄位，區分本次修改與沿用前提，不能只列設定名稱 |
| 使用者驗收 | API 方法與路徑或指令、實際輸入、預期結果；錯誤輸入、重傳或資料隔離案例依需求選擇 |
| 通過判準 | 可觀察的回傳欄位、匯出值或唯讀查詢結果；不只寫「確認正常」 |
| 驗證與待辦 | 已執行的自動測試與結果列於驗證明細；本案所需 SQL Server／真實 Excel／實際 API 驗收的待辦及完成狀態只列在最上方 checkbox，不在明細重述 |
| 呈現方式 | 依內容選擇短段落、條列、步驟、表格或圖表；複雜關係可用流程圖，不為套格式增加章節或圖表 |

涉及資料隔離時，使用不同範圍的測試資料，驗證更新其中一組不影響其他組；具體鍵值、操作與預期結果依當次程式及需求決定。

使用者明確要求完整 JSON 時沿用既有 Schema：SQL 所在的 Notion 工作卡連結／明細名稱、操作及預期結果記入 `solution_steps`，執行證據記入 `test_results`；`user_reply` 只保留簡短結論、必要的使用者動作及同卡連結，不要求 SQL 檔案路徑。`changed_files` 只記本次實際修改的檔案，只有 Notion／SQL 內容交付而無 repository 異動時填 `[]`，不為填報告而建立交付文件。
